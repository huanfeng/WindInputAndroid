# 键位映射与皮肤自定义：规划

> 2026-11-24 草案（只规划，未动代码）。覆盖反馈里的 F1（上滑 / 下滑 / 长按自定义）与 F6（皮肤自定义、字母行间距、键盘大小协调、按键上方符号自定义），顺带收 B6（默认皮肤吃掉方案自带直通键位）。
> **2026-11-24 已拍板的原则**：①**出厂默认布局一律不变**——本方案只增加「自定义」能力，不动任何默认键位 / 角标 / 几何；不设置覆盖的用户看到的键盘与现在逐像素一致。②**下滑符号要做**，且进第一阶段（主流手机输入法都有；参考图里下滑多是功能：全选 / 剪切 / 复制 / 粘贴 / 历史 / 段首 / 段尾，所以下滑从一开始就要能绑 `Func`，不止字符）。
> **2026-11-24 第二轮拍板**：①R6：左符号自动配对、右符号单出，不做其它处理（主流做法，也容得下用户删掉右符号）。②键位覆盖用**单独文件**，且**放在移动端独有的 `<userRoot>/mobile/` 下，文件名与目录都不与 PC 的 `config.toml` / `themes/` / `schemas/` 等同名**——后续要做数据同步，同步时按目录区分「PC 的」「手机的」「通用的」。③移动端皮肤**不复用 `wind-theme`**：PC 有独立的三平台渲染架构，手机完全不同，只借鉴思路；甚至建议**不用 Rust 实现**。皮肤范围不止几何参数，要含背景图片、定位等，另见 `docs/mobile-skin-design.md`。④左右滑不做。⑤空格上滑 / 中英键预编辑时作次选（R7）：空位，可做，**提供功能开关**。⑥反馈者补信息的事先记录，后续处理。
> 相关文档：`docs/architecture.md` §3.3 / §3.4（目录与主题）、`docs/android-ime-features.md` §5 / §14（外观与主流布局对照）、`docs/toolbar-numpad-undo-plan.md`。

## 1. 现状盘点

### 1.1 键位数据（`keyboard/KeyboardLayout.kt`、`LayoutRepository.kt`）

- **键位模型**：`KeyDef(label, action, widthWeight, isSpecial, swipeUp: Char?, longPress: String, enText, enSwipeUp, rowSpan, isAccent)`。
  - `action` 是封闭 sealed：`Text(char)`、`Commit(text)`、`Backspace / Enter / Space / Shift / SwitchSymbols / SwitchLang / Emoji / SymbolPage / NumberPad / Spacer`。
  - **只有「上滑」一个方向**，且只能是**单个 `Char`**，不能是字符串、短语或动作；没有「下滑」；没有左右滑。
- **长按**：字母键气泡固定为 `[大写 | 上滑符号 | 小写]`（`popupChars()` 现算，不读 `long_press`）；非字母键用布局里的 `longPress` 字符串（每字符一项）。空格、退格、`SwitchLang` 的长按走 `KeyboardView.Listener.longPressOptions` 和手势状态机，是另一套代码。
- **布局来源**：`assets/data/layouts/{qwerty,symbols,number}.toml`，解析器 `LayoutParser`。覆盖解析为 `<userRoot>/keyboard/layouts/*.toml` > `filesDir/data/layouts/*.toml` > 代码内置（`KeyboardLayouts`），整文件替代，解析失败静默回退。
  - 用户今天**能**手改 `qwerty.toml` 改上滑符号，但：要用文件管理器进 `Android/data/<包>/files/keyboard/layouts/`；整文件复制后，出厂布局升级时用户拿不到新增内容；没有任何设置页入口。
- **运行时改写**：`LayoutTweaks`（纯函数，按**动作**认键，认不出就放过）按设置项 `ui.android.bottom_row`、`ui.android.number_page` 改底行和数字页切换键。这是目前唯一的「设置 → 布局」通道。
- **符号来源**：
  - 上滑 / 长按符号**键面一律写 ASCII**，中文形态由 `Punct.display()` 现算（`, . ? ! : ; ( ) < > [ ] { } \ ~ ^ $ \` _ " '`）；输出走核心 `press`，中文标点转换、智能配对、全半角都是引擎的事（`Punct.kt` 头注释，这条原则要保持）。
  - 非 ASCII 字面字符（现在只有 `”`）引擎翻不出 VK，`symbolActionFor()` 直接 `Commit`。**这是现有的唯一一条「绕过引擎直接上屏」的口子**。
  - 分类符号页（`symbol_pages.toml`）已有用户层覆盖：`filesDir/user/symbol_pages.toml`，同样整文件替代。《》〔〕「」·全在「中」「括号」页里，只是要进符号页才能点到。

### 1.2 手势（`KeyboardView.kt`）

- 上滑：`dy > swipeActivatePx(16dp)` 且纵向为主 → 弹气泡；`dy > swipeThresholdPx(40dp)` 才「选中」；抬手时 `swipeArmed` 才输出 `key.swipeFor(englishMode)`（`symbolAction(c)` → 引擎或 `Commit`）。
- 总开关 `ui.android.gesture_swipe_symbols`（默认开）和角标开关 `ui.android.show_swipe_hints`；设置由 `WindInputImeService` 从 `userConfig`（键盘自己的 `keyboard/config.toml`）读后写到视图字段。
- 长按延迟 `longPressDelayMs = 300`，已可配。
- 振动：`KeyHaptics.kt` 统一封装，覆盖范围反馈见 F7，不在本文范围。

### 1.3 外观（`Palette.kt`、`KeyboardDimens`）

- **颜色**：`Palette` 15 个语义槽位，仅内置 `light` / `dark` 两套，设置 `ui.android.theme` 选 `light | dark | 跟随系统`。注释已写明「将来 wind-theme 求值出来的调色板也填进这同一组槽位，视图层一行不用改」——**接口已留好，数据源没接**。
- **几何**：
  - 可配：`ui.android.row_height_portrait / landscape`（40–72 / 36–64dp，**高度改了要重建视图才生效，即反馈 B3，已修**）、`keyboard_bottom_gap`、`keyboard_side_gap`、`one_hand`。
  - **全是编译期常量**：键间距（`KEY_GAP_DP = 2.7`、`EDGE_PAD_DP = 3.4`）、圆角（`KEY_RADIUS_DP = 8`）、键帽高度（`KEY_HEIGHT_DP = 51`）、行间距 = `rowHeight − 51dp`。
  - 因此「字母每排间隙可调」今天**只能通过改行高间接实现**，键帽高度恒 51dp：行高 72 时行间距 21dp，行高 56 时仅 5dp，两个量绑死。「键盘大小不协调」的一部分原因可能就在这里（需要反馈者补机型）。
- **字体**：字号、角标字号都是视图内常量；键面字重、候选字体走别处。
- **图标**：`KeyIcons.kt` / `IconSet.kt` / `PanelIcon.kt` + 用户层 `keyboard/icons/`（目录已预留）。

### 1.4 用户配置存储与迁移

| 层 | 路径 | 内容 | 迁移现状 |
|---|---|---|---|
| 出厂层 | `filesDir/data/` | 布局、符号页、主题数据 | 每次升级整体重放，**用户不可编辑** |
| 用户根 | `getExternalFilesDir()`（Android 17 之后按记忆是「应用 files 目录」，已做迁移） | 核心 `config.toml`、`schemas/` | 核心管 |
| 键盘用户层 | `<userRoot>/keyboard/` | 键盘自己的 `config.toml`（`ui.android.*`）、`layouts/`、`icons/` | 无版本号、无迁移机制 |

关键事实：键盘配置**没有 `version` 字段**，整文件替代式覆盖又意味着一旦出厂布局改了结构，用户的旧覆盖文件会悄悄用着旧结构。这是本方案最需要先补的地基。

### 1.5 与 B6（默认皮肤吃掉方案自带直通键位）的关系（待查，未证实）

反馈：默认皮肤好像会吃掉方案自带的「直通方案」使其不生效（小鹤音形）。从代码能推出的可疑点，**都只是假设，需要先在靶机 PC 上取到对应方案再复现**：

1. 默认布局里**非字母键全是硬编码 ASCII `Text`**（逗号、句号、第一行上滑数字、各字母上滑标点）。方案如果在 `[keys]` 里把 `;`、`'`、数字行等定义为编码键 / 直通键（小鹤音形一类，双拼里 `;` 常被占用），键盘根本没有对应的按键位置，**上滑出来的标点又走引擎的标点转换**，与方案期望对不上。
2. 布局不随方案变化：同一份 qwerty 布局服务所有方案，方案无法声明「本方案把某键的上滑 / 长按禁掉或改成别的」。
3. `LayoutTweaks` 的「逗句号合一」改写只认动作、不认方案。

→ 第 0 阶段先**查清到底是哪个键、哪条链路吃掉了**，再决定落在哪一层（见 §3.4）。

**核对结果（2026-11-24，已用 Rust 探针实测，探针未提交）**：方案的键位声明**基本都被遵守**，缺口在默认布局上缺「引导键」的触点，而不是被皮肤「吃掉」。

- 触屏的 ASCII 上滑 / 长按一律以 `KeyAction.Text` 原样进核心（`KeyboardView.kt:1341`、`wind-mobile` `touch.rs:240-255`），`key_actions`、选词键都能看到。只有 123 页数字、符号页和非 ASCII 字面字符走 `Commit` 绕过引擎。
- 实测遵守：`;` 作次选（小鹤双拼 `xi;` 选第 2 候选）、`;` 作 ing（搜狗 / 微软 / 紫光 `l;` → 令/另/零/领）、`z` 万能键、双拼下 `` ` `` 按声明走辅助码（辅助码出厂关时落普通标点，与 PC 一致）。
- **不可达 / 触点深**：①**反引号 `` ` `` 键盘上没有触点**（临时拼音与双拼辅助码的引导键；仅工具栏「拼」按钮合成可达）；②`;` 只在 n 上滑 / 逗号长按，对高频用 `;` 的搜狗 / 微软 / 紫光双拼用户太深；③`'` 等同理；④符号页的 `Commit` 路径点不了引导键。
- **小鹤音形的前提有误**：`;` 作 ing 是搜狗 / 微软 / 紫光的约定，小鹤的 ing 是 `K`，`xiaohe.toml` 里没有 `;`。所以 **B6 仍未解释**——「直通方案」更可能指命令直通车（`$CC(…)`、`command:` 绑定）。要反馈者说清是哪个键、什么现象。
- **修法（并入本方案，不改默认布局）**：阶段 1 的预设里提供「双拼」「辅助码」等**引导键预设**——把 `;`、`` ` `` 放到字母行旁或常驻位置；符号页对「声明为引导键」的字符改走 `press` 而非 `commitDirect`（移动端改动，不影响 PC）。

## 3. 统一数据模型

### 3.1 分层与合并（核心设计）

把「键盘长什么样、按键出什么」拆成**三层 + 一层方案声明**，自下而上合并，后者覆盖前者**按键位粒度**而不是整文件：

```
L0 代码内置兜底      KeyboardLayouts（现有，最后一道防线）
L1 出厂布局          filesDir/data/layouts/*.toml（现有，升级重放）
L2 方案声明          schema.toml 里的 [keyboard]/[keys] 声明（新增，可选，见 §3.4）
L3 用户覆盖          <userRoot>/mobile/keymap.toml（新增，只存「改了什么」）
```

- **按键位覆盖，不整文件替代**：L3 只写差异，形如 `[layer.letters.key.a.swipe_up]`。出厂布局升级后，用户没动过的键自动跟着升级，动过的保持用户的。现有的整文件覆盖（`layouts/*.toml`）**保留**，作为高级用户的「整份换掉」逃生口；二者同时存在时整文件覆盖先生效，再叠 L3。
- **键位身份**：布局里每个键要有稳定的 `id`，覆盖才有锚点。字母键用 `layer.letters/a`、底行用动作名（`bottom.comma`、`bottom.period`），认不出的键（布局被用户整文件改过）覆盖项**跳过并记日志**，沿用 `LayoutTweaks`「认不出就放过」的原则。
- **合并后产物仍是 `List<List<KeyDef>>`**：下游（`KeyboardView`、`LayoutTweaks`）几乎不改。合并在 `LayoutRepository` 内完成，结果按 `(各层文件 mtime+length, 方案 id, 模式)` 缓存，沿用现有缓存键。

### 3.2 手势与动作

把 `KeyDef` 里孤立的 `swipeUp: Char?` / `longPress: String` 收成一个手势表，动作类型扩成 sealed：

```kotlin
enum class Gesture { TAP, SWIPE_UP, SWIPE_DOWN, LONG_PRESS /* 气泡 */, (后续) SWIPE_LEFT, SWIPE_RIGHT }

sealed interface KeyOutput {          // 手势触发的「做什么」
    data class Char(val c: kotlin.Char) : KeyOutput          // 现有 Text：经引擎，中英形态随模式
    data class Text(val text: String) : KeyOutput            // 原样上屏，不经引擎（现有 Commit，含 ·《》〔〕）
    data class Template(val tpl: String) : KeyOutput         // 日期/时间模板，上屏时现算：{date} {time} {weekday}…
    data class Phrase(val id: String) : KeyOutput            // 引用短语库条目（不新建第二套短语存储）
    data class Func(val name: String) : KeyOutput            // 功能：punct_toggle / one_hand / undo / redo / symbol_page / clipboard…
    // 现有的 SwitchLang / Emoji / NumberPad 等归入 Func，由一张「名字 → 现有 KeyAction」表映射
}

data class KeyDef(…, val gestures: Map<Gesture, GestureDef>)
data class GestureDef(
    val output: KeyOutput,
    val enOutput: KeyOutput? = null,         // 英文模式覆盖（现有 enText / enSwipeUp 泛化）
    val label: String? = null,               // 角标显示，缺省由输出推出
    val bubble: List<KeyOutput> = emptyList(),// 仅 LONG_PRESS：多项气泡（现有 longPress）
)
```

要点：

- **`Char` 与 `Text` 分开是有意的**。`Char` 走引擎，沿用「键面写 ASCII、中英形态由模式派生、K 侧不做转换」这条已被验证的原则；`Text` 是用户明确要的字面文本（`《`、`·`、短语），原样上屏。**不为了好写而把用户填的中文标点悄悄转成 `Char`**，否则又长出第二份转换逻辑。
- `swipeUp` / `longPress` / `enText` / `enSwipeUp` 变成 `gestures` 的便捷读取器（保留同名属性），**第 1 阶段 `KeyDef` 的外部接口不变**，视图与现有测试不用动。
- 功能动作（`Func`）用**名字白名单**，不开放任意代码；未知名字 = 无动作并在设置页标红。
- 空格 / 退格 / 中英键的**既有手势（移光标、扩选、长按切方案）保持独立状态机**，不并入手势表。用户覆盖只允许改它们**剩下的空槽**（例如空格上滑，R7），避免把成熟的手势机拆坏。

### 3.3 TOML 形态

出厂布局保持现有写法（`swipe_up = "~"` 继续有效，等价于 `gestures.swipe_up = { char = "~" }`），新增表形式给用户覆盖用：

```toml
# <userRoot>/mobile/keymap.toml
version = 1

[layer.letters.key.z]            # 上滑 / 下滑 / 长按
swipe_up   = { text = "《" }
swipe_down = { text = "》" }
long_press = ["〔", "〕", "·", "—"]   # 气泡项，顺序即位置

[layer.letters.key.x]
swipe_up   = { template = "{date}" }
swipe_down = { func = "undo" }

[layer.letters.bottom.comma]     # 底行逗号：用动作名定位，不依赖下标
long_press = ["，", "；", "：", "“", "‘", "、"]

[when.auto_pair.chinese]         # 见 §3.5：配对开启时的差异化
"layer.letters.key.z".swipe_up = { text = "（" }
```

### 3.4 与方案自带键位的关系（含 B6）

- **原则**：键盘是**方案的宿主**，方案可以对键位表态，但表态范围只限「禁用 / 改成」某些手势，不能新增功能键、不能改布局结构。
- **方案声明**（L2，可选）：`schema.toml` 里新增 `[keyboard.keys]`（或复用现有 `[keys]` 域），写法同 L3，用于「本方案占用了 `;`/`'`/数字行，请把对应上滑改成 X 或禁掉」。主仓核心不需要识别它——**由手机端宿主在读方案时解析**，核心无感，对 PC 零影响。
- **优先级**：`L3 用户 > L2 方案 > L1 出厂`。理由：方案作者最清楚自己的键位被占用，用户的显式选择又高于一切；但用户**没碰过**的键，方案声明应当生效——这正是 B6 要的效果（小鹤音形声明后，默认皮肤不再吃掉那几个键）。
- **B6 的具体修法不在这里先定**，等第 0 阶段取到小鹤音形实际包、确认是 §1.5 的哪条后再选：(a) 方案声明；(b) 布局按方案类别自动换一套上滑表；(c) 仅是 bug（某条链路没把按键放行给引擎）。先别为猜测建抽象。

### 3.5 「中文标点自动配对」规则（R6）——已定：不做特殊处理

**结论（2026-11-24）**：左符号（`（` `“` `《` 等）由引擎自动配对，右符号单独上屏，**不做任何额外处理**。这是主流输入法的做法，也能容纳用户手动删掉右符号的情况（引擎的跳出逻辑 `jump_out_keys` 只在确有配对状态时生效）。

所以本方案**不再需要**「配对开启时的推荐表」「条件段 `[when.auto_pair.chinese]`」「配对精简预设」，也不用为它监听 `auto_pair.chinese` 变化。原先担心的「键面上摆着一对显得多余」，通过用户自己覆盖上滑符号（阶段 1，书名号 / 〔〕 / · 可配）解决，而不是由键盘替用户改默认。

### 3.6 皮肤（F6）

**架构决定（2026-11-24）**：移动端皮肤**不复用 PC 的 `wind-theme`**。PC 端有独立的渲染架构、三平台共用；手机端的绘制（Canvas / Bitmap / 位图缓存 / 深浅色 / 动态取色）完全不同，复用只能停在「逻辑思路」这一层（槽位命名、深浅色双态、预设）。因此**求值与绘制全在 Kotlin 侧**，不经 FFI、不碰核心——这也让皮肤改动对 PC 零影响。

范围也不止几何参数：除键间距 / 行间距 / 圆角 / 字号外，**背景图片、定位（左右偏移、底部留空、单手位置）、按键态颜色、字体**都要纳入。完整设计（数据模型、背景图的缩放 / 裁剪 / 深浅色 / 横竖屏、位图内存预算、包格式、同步友好的文件布局、分阶段）见 **`docs/mobile-skin-design.md`**，本文只保留与键位映射相关的接口：

- **几何参数化**（最先做，改动面小）：`KEY_GAP_DP / EDGE_PAD_DP / KEY_RADIUS_DP / KEY_HEIGHT_DP` 变成 `KeyboardDimens` 的可注入变量，行高与行间距解耦（取代「行高 − 51」的隐式推导），键帽高度保证 ≥ 40dp，设置页给范围而不是事后报错。「字母每排间隙可调」= `row_gap`。
- 皮肤与键位映射**数据分离**：皮肤在 `mobile/skins/`，键位覆盖在 `mobile/keymap.toml`，互不引用，各自带版本号。

### 3.7 配置存储与版本迁移

- 新增 `<userRoot>/mobile/keymap.toml`（键位覆盖）与 `<userRoot>/mobile/skins/`（皮肤包，见皮肤设计文档）。`keymap.toml` 与每个皮肤的描述文件都**首行 `version = N`**。
- **读取规则**：版本号高于当前支持 → 忽略整个文件并在设置页提示「配置来自更新版本」，**不覆盖、不删除**；缺失版本号按 `1`；字段名拼错 / 未知手势 / 未知 `func` → 跳过该项并写日志，**不让整份覆盖失效**（与现有「解析失败回退」同一哲学，但粒度更细）。
- **出厂布局升级**：因为覆盖是按键位的差异，升级时不需要迁移用户文件；只有「键位 `id` 改名 / 删除」才会让覆盖项失效。约定：**布局键位 `id` 一经发布不改名**，必须改时在 `keymap.toml` 的读取处加一张旧 `id` → 新 `id` 映射表，并加单测。
- **配置键位（`ui.android.*`）**：沿用 `settings_manifest.toml` 的 `[[item]]` 声明、`userConfig` 读写；新增项都带 `default`，没有就等于旧行为，**无需迁移**。
- **同步友好（后续要做数据同步）**：移动端文件一律放 `<userRoot>/mobile/` 下，**不使用 PC 已有的文件名 / 目录名**（`config.toml`、`themes/`、`schemas/`、`state.toml`、`wind_setting.toml` 等），同步时按目录划分归属，不会互相覆盖。`keymap.toml` 里的键位覆盖是**逻辑配置，可跨设备同步**；皮肤里与屏幕尺寸相关的值（行高、边距、留空）是**设备相关，不应跨设备同步**，详见皮肤设计文档。
- **备份**：`mobile/` 目录都在现有备份通道（`DictBackup` 同类机制）的目录内，加入导出清单即可，不新开格式。

## 4. 设置页方案

手机上不做自由编辑器，**「预设 + 单键覆盖」**两层：

1. **预设（第 1 阶段就有，成本最低）**：「键盘 → 键位」下加一项「上滑符号方案」：`默认（小米式）｜标点优先｜数字优先｜配对精简（R6）｜自定义`。预设是出厂提供的几份 `keymap` 片段，选中即写入 L3 的 `preset = "…"` 一个字段，不展开成差异。
2. **单键覆盖（第 2 阶段）**：新页「自定义键位」——
   - 顶部放一个**可点选的键盘缩略预览**（复用设置里已有的 `preview = "keyboard_rows"` 机制），点某个键 → 进入该键的编辑面板；
   - 面板里分「点按 / 上滑 / 下滑 / 长按」四行，每行一个**类型选择 + 一个输入**：`单个字符`、`文本`、`日期时间模板`、`短语`、`功能`（下拉白名单）、`无`；
   - 输入框旁给**常用符号快捷条**（`《》〔〕「」·—…`）与「从符号页挑」入口，避免用户在手机上手敲中文标点；
   - 每行右侧**恢复默认**；页头**全部恢复默认**；改动**实时刷新预览键盘**，退出页面才落盘（避免半成品）。
3. **皮肤页（第 3 阶段）**：「键盘 → 外观」分「间距与大小」（滑块，带实时预览）和「颜色」（15 槽位的色块选择，先给 3–5 套预设主题）。**所有滑块带「恢复默认」**，因为几何参数一旦调乱，用户很难自己回来。
4. **文件入口保留**：高级用户仍可直接编辑 `keymap.toml`；设置页顶部给「重新载入」按钮，作为「手改文件」的反馈通道。

不做：拖拽调整键位顺序、新增 / 删除整个键、整行重排（那是布局编辑器，成本高，需求未出现）。

## 5. 对 PC 端与核心的影响

- **核心零改动是硬约束**：键位、皮肤、方案声明解析全在手机端宿主（Kotlin）。核心只通过现有 `press`（`Char`）与现有读写设置的通道交互。
- `Text`（原样上屏）、`Template`、`Phrase` 都在宿主侧产出最终字符串后调现有上屏接口；`Phrase` 只**读**短语库，不新增存储。
- 方案声明 `[keyboard.keys]` 是 schema.toml 里的新段：PC 端核心不认识这个段，按「未知键忽略」处理即可。**实施前要在主仓确认 schema 解析对未知段是宽容的**，有测试覆盖（若不宽容，改走手机端独立的 `schema_overrides` 同类文件，而不是改核心）。
- 皮肤**不碰 `wind-theme`、不经 Rust 求值**（见 §3.6 的架构决定），因此不存在「改核心共用代码」的风险。
- 与 B3（设置变更刷新）共用「设置 → 键盘重建」通知，不另起机制。

## 7. 风险与待决问题

**风险**
- **手势冲突**：上滑 / 下滑 / 长按气泡与退格扩选、空格移光标、字母键长按、触摸 `-` 误判翻页（已修）共享同一套触摸判定；B4「手指碰到字母没上屏」也出在这一带。**阶段 2 动手势前先把 B4 的触摸丢键查清**，否则新增手势会把问题放大。
- **整文件覆盖与按键位覆盖并存**会让「用户到底改了什么」难解释，设置页要能显示「当前键位来自：出厂 / 方案 / 你的覆盖」。
- **`Char` 与 `Text` 的边界**：用户把标点填成「文本」会绕过引擎的智能引号 / 配对 / 全半角，设置页要在这种情况给一句提示，并默认引导填 ASCII（让引擎按模式出形态）。
- **功能动作的白名单**要和快捷面板、工具栏共用同一张动作表，否则长出第三套。
- 键帽高度解耦后，旧用户行高设置在新几何下的观感会变；阶段 3 默认值要保证「不动设置的人看起来不变」。

**已定（2026-11-24）**
1. **R6**：左符号自动配对、右符号单出，不做其它处理（§3.5）。
2. **L3 文件格式**：单独 `keymap.toml`，放 `<userRoot>/mobile/` 下，**与 PC 路径 / 文件名不冲突**，为后续数据同步留余地（§3.7）。
3. **方案声明**：方案本身已有键位声明（`[key_actions]`），要先**核对手机端是否遵守**，再决定要不要加手机端专属的声明。核对结果见 §1.5。
4. **皮肤**：不复用 `wind-theme`，Kotlin 侧独立实现；范围含背景图片、定位等，见 `docs/mobile-skin-design.md`。
5. **左右滑**：不做（非主流）。
6. **R7**（预编辑时空格上滑 / 中英键作次选）：做，用它们剩下的空槽，**提供功能开关**（默认值待定，建议默认关，与「默认行为不变」一致）。
7. **反馈者补信息**（「键盘大小不协调」的机型与截图；B6 具体现象）：先记录，后续再处理。荣耀 Magic8（B8）与本方案无关，已单独走诊断导出。
